# design-better

The design lead for the Trifolium admin console. The console was generated by an
AI from a product brief and it shows: the right palette, the wrong everything
else. This skill replaces it piece by piece with design that belongs to a
compounding pharmacy — calm, exact, dense, trustworthy — and leaves behind a
written language so the next person (or model) cannot regress it.

Two documents in `references/` are the memory of this work. **Read both before
every task**, however small:

- `references/language.md` — the brand facts that are signed and stay, the
  direction set so far, and the decision log. Every task ends by appending to it.
- `references/refusals.md` — the generic patterns this console refuses, each
  with what replaces it, and the things that are already right and must survive.

`references/system.md` is the inventory of what exists (components, classes,
constraints). `scripts/tokens.sh` prints the live tokens from `admin.css` —
run it rather than quoting values from memory; the stylesheet is the truth.

## 1 · Mandate and limits

**The mandate is broad.** Palette, typography, spacing, chrome, composition,
base components — all of it is open, screen by screen or system-wide. The one
thing that is not open is the brand itself: the deep sage green, the dandelion
mark and the serif wordmark were approved and signed by the client on
10.7.2026 (see `language.md` §1). We design *from* them, never past them.

**The limits are the product's, not the prompt's.** This is an operations
console used eight hours a day by three or four pharmacy staff, in Hebrew, on
tables of thousands of rows. Speed and legibility outrank delight. A technique
that would win an award on a marketing site is a liability here unless it
makes a row easier to read or a decision faster to take.

Standing rules from Avichai that survive the redesign:

- Every field gets its own label. Never a header row over bare inputs.
- The demo must feel completely real — real Hebrew, real numbers, real states.
- RTL first; every screen is verified in English too. No Hebrew literal in a
  `.vue` file — `check:i18n` fails the build on it.
- No new dependency without approval. The bundle already carries PostgreSQL.
- Commit and push after every finished piece, and say so.
- When in doubt, do not build — ask. Questions at the start and the end.

## 2 · The workflow — seven steps, one hard stop

Every task, whether a button or the whole type system, walks these in order.

### 0 · Intake
What arrived: a screenshot, a screen name, a component. Establish in one line
each: what the thing is *for*, who stands in front of it, how many times a day,
and what the user does right after reading it. If any of those is unknown, ask
before step 1 — a redesign that does not know the job cannot be judged.

### 1 · Read
Read the component's source, its siblings in the same folder, the shared
classes it leans on in `admin.css`, and the tokens (`scripts/tokens.sh`). Note
which parts are the project's own system (`.a-*`, the UI components) and which
are the component's private styles. Open it in the browser in both languages.

### 2 · Diagnose — in writing, before any design
Three lists, each a few lines:
- **Generic** — what reads as template: the patterns in `refusals.md`, named.
- **Broken** — hierarchy, spacing, contrast, RTL slips, states that are missing.
- **Right** — what already works and must survive. *A redesign that changes
  everything proves nothing.* Name what stays, explicitly.

### 3 · Direction
First the language in words — five lines at most: the idea, the typographic
move, the colour move, the spatial move, what is being removed. Then **two or
three variants as mockups**, each with a name and a one-line thesis that makes
it different from the others in kind, not in degree. Three shades of the same
idea is one variant.

Mockups are HTML pages published as artifacts (load the `artifact-design` skill
first; write the file to the scratchpad). Rules for a mockup:
- `<html dir="rtl" lang="he">`, the real fonts (Assistant / Inter from Google
  Fonts, Cormorant Garamond only where the wordmark appears), the real tokens
  pasted from `tokens.sh` — a mockup in invented colours proves nothing about
  the console.
- Real content: the Hebrew strings the screen actually uses, real-looking item
  codes, quantities and prices in tabular numerals, the real states (a row
  needing attention, an empty table, a locked gate).
- One page, variants side by side or stacked with their names, at 1440px with
  the sidebar accounted for. A toggle to view each at laptop width if layout
  is the question.
- No business logic, no persistence, no framework. Static HTML and CSS; a few
  lines of script only to switch variants.

### 4 · ⏸ Consult — the hard stop
Present in Hebrew: the diagnosis, the language, the variants with their theses,
and a recommendation with the reason. Then **stop and wait**. Nothing in
`resources/` changes before Avichai answers. If the answer is a mix ("A with
B's table"), restate the merged direction in three lines and confirm it before
building. If the answer raises a system-level question (see §3), say so and
scope it as its own task.

### 5 · Build
Implement the approved direction in the existing architecture:
- Extend the `.a-*` system and the shared UI components rather than adding
  private styles; a new pattern that two screens need becomes a shared class
  or component, named in the project's voice.
- Logical properties for direction (`margin-inline-start`, `inset-inline-end`,
  `text-align: start`); never `left`/`right` for layout that mirrors.
- Every string through `t()`, both catalogs updated in the same change.
- Tokens change in `admin.css` `:root` only. A new token is documented in
  `system.md` in the same commit.
- Prettier, then `eslint --fix --max-warnings 0`. Never format the data folder
  (`resources/js/demo/real` is ignored on purpose).

### 6 · Verify
`npm run verify:prod` must be green. Then the browser: the screen in Hebrew and
in English, at desktop and laptop width, every state the diagnosis listed, the
console clean of errors. Take screenshots as proof — the report shows them,
it does not describe them. Compare against the approved mockup; a deviation is
either fixed or named in the report with its reason.

### 7 · Record and ship
Append to `references/language.md` §4, three lines: *what it was · what was
decided · why*. Update `system.md` if a token, class or component was added.
Commit with the project's commit voice (Hebrew subject, the reasoning in the
body) and push. The report ends with the commit hash.

## 3 · System-level tasks are different

A change to the type scale, the radius, the neutral ramp, the base button,
input or table touches every screen at once. Such a task:
- is always its own task, never folded into a screen redesign;
- lists the affected screens before the mockups (count them with `grep`);
- shows its variants on **two real screens of different kinds** — a dense table
  screen and a form/drawer screen — not on a palette swatch;
- after approval, lands as one commit per primitive (type, then radius, then
  neutrals…), each verified across the listed screens, so a regression has an
  address.

**The first task of this skill is the system** — that was the agreed order.
Screens come after, on the new base.

## 4 · The stance — what good looks like here

- **Apothecary, not dashboard.** Flat surfaces, hairline borders, depth by
  tone (sunk vs raised surfaces) rather than shadow. Materials, not elevation.
- **Structure is information.** A number, a rule, a label, a colour appears
  because it tells the reader something true. Decoration has no seat.
- **One accent per screen.** The sage green marks the one primary act. Status
  colours (amber, blue, teal, green, red, purple) say state and nothing else.
- **Hebrew sets the type.** Assistant for interface Hebrew; Latin, codes and
  numbers in Inter inside LTR islands; `tabular-nums` wherever digits align.
  The serif (Cormorant Garamond) is the brand's voice and appears once — in
  the wordmark — never as a heading face.
- **Density is the feature.** The reader wants more rows, not more air. Space
  goes between groups, not inside every cell.
- **Every state is designed.** Empty, loading, error, locked, zero — in the
  console's own vocabulary (thin sage line illustration, plain sentence, one
  action), never a grey icon and "No data".
- **Motion has a job or is absent.** ≤150 ms, opacity and transform only, on
  state change — a drawer opening, a row settling. Nothing on load, nothing
  on hover that is not a state.
- **Keep what is right.** The chip system, URL-as-state, the single table
  component with its own scroll bar, the chip strip, labelled fields, the
  approval gates, confirmation dialogs that say what will happen — these are
  the console's good bones. See `refusals.md` §3.

## 5 · Reporting

All conversation with Avichai is in Hebrew; code, class names, tokens, file
paths and commit subjects stay as they are and sit on their own line or in a
code span. The report after step 7 is short and has fixed parts: what was
diagnosed, what was decided and why, files changed, checks run and their
result, screenshots, the commit, and anything left open — as a question, not a
guess.

## 6 · Before presenting (step 4) — check

- The job of the component is stated and the diagnosis names what stays.
- Variants differ in kind. Each has a name and a one-line thesis.
- Mockups use the live tokens and the real fonts, in RTL, with real content.
- The recommendation says why, in terms of the reader's task.
- Nothing in `resources/` has changed.

## 7 · Before committing (step 7) — check

- `verify:prod` green; Prettier and ESLint clean; no Hebrew literals in `.vue`.
- Verified in the browser in both languages; screenshots taken.
- Every field labelled; logical properties; strings in both catalogs.
- No new dependency; `demo/real` untouched.
- `language.md` has the three-line entry; `system.md` updated if needed.
- The commit message carries the reasoning, not just the change.
